# Ritual Festivals

Ritual festivals are repeatable festival templates that can be run multiple times. Each run creates a new copy in `active/` while the template remains in `ritual/` untouched.

## When to Use Rituals

Use ritual festivals for recurring work patterns:

- Weekly code reviews
- Monthly retrospectives
- Sprint planning sessions
- Recurring maintenance tasks
- Any workflow you repeat on a schedule

## Creating a Ritual

Create a ritual festival with the `--type ritual` flag:

```bash
fest create festival --name "weekly-review" --type ritual
```

This creates the festival in `festivals/ritual/` instead of `active/`:

```
festivals/ritual/weekly-review-RI-WR0001/
├── FESTIVAL_GOAL.md
├── FESTIVAL_OVERVIEW.md
├── fest.yaml
└── ...
```

### Ritual ID Format

Ritual festivals use the `RI-` prefix in their ID:

| Type | ID Format | Example |
|------|-----------|---------|
| Standard | `XX0001` | `api-refactor-AR0001` |
| Ritual | `RI-XX0001` | `weekly-review-RI-WR0001` |

The `RI-` prefix is generated by `id.GenerateRitualID()`.

## Running a Ritual

Use `fest ritual run` to create a new instance:

```bash
fest ritual run weekly-review-RI-WR0001
```

This copies the template to `active/` with a hex counter appended:

```
festivals/active/weekly-review-RI-WR0001-0001/
├── FESTIVAL_GOAL.md
├── FESTIVAL_OVERVIEW.md
├── fest.yaml
└── ...
```

### Run Counter

Each run gets an auto-incrementing 4-digit hex counter:

| Run | Directory Suffix |
|-----|-----------------|
| 1st | `-0001` |
| 2nd | `-0002` |
| 10th | `-000A` |
| 255th | `-00FF` |
| 65535th | `-FFFF` |

The counter is determined by scanning these directories for existing runs:

1. `festivals/active/` -- active runs
2. `festivals/dungeon/completed/` -- completed runs (all date subdirectories)
3. `festivals/dungeon/archived/` -- archived runs

The highest existing counter is found and incremented by one.

### Matching Rules

You can specify the ritual by:

1. **Exact directory name**: `weekly-review-RI-WR0001`
2. **Festival ID**: `RI-WR0001`
3. **Substring match**: `weekly-review` (case-insensitive)

## RitualConfig in fest.yaml

When a ritual is run, its `fest.yaml` is updated with run metadata:

```yaml
ritual_config:
  schedule: "weekly"        # "weekly", "daily", "monthly", "manual", or cron
  last_run: "2026-02-10"   # ISO date of most recent run
  run_count: 3             # Total number of runs (decimal)
```

### Fields

| Field | Type | Description |
|-------|------|-------------|
| `schedule` | string | Run frequency: `weekly`, `daily`, `monthly`, `manual`, or a cron expression |
| `last_run` | string | ISO date (YYYY-MM-DD) of the most recent `fest ritual run` |
| `run_count` | int | Total number of times this ritual has been run |

The `schedule` field is informational only -- `fest` does not currently auto-schedule runs. The `last_run` and `run_count` fields are updated automatically by `fest ritual run`.

## Lifecycle of a Ritual Run

Each ritual run follows the standard festival lifecycle:

```
ritual/ (template, stays here)
    |
    |-- fest ritual run -->  active/  (new copy with counter)
                               |
                               |-- fest promote -->  completed (dungeon/completed/YYYY-MM/)
```

The template is never moved. Only the run copies progress through the lifecycle.

## Example Workflow

```bash
# 1. Create a ritual template
fest create festival --name "sprint-retro" --type ritual --goal "Sprint retrospective"

# 2. Add phases and structure to the template
fest create phase --name "REVIEW" --festival sprint-retro-RI-SR0001

# 3. Run it for the first time
fest ritual run sprint-retro-RI-SR0001
# -> active/sprint-retro-RI-SR0001-0001/

# 4. Complete the run
cd festivals/active/sprint-retro-RI-SR0001-0001/
fest promote  # -> ready -> active -> completed

# 5. Next sprint, run again
fest ritual run sprint-retro-RI-SR0001
# -> active/sprint-retro-RI-SR0001-0002/
```
