================================================================================
                    FEST CLI - GETTING STARTED GUIDE
================================================================================

Welcome to the Festival Methodology CLI! This guide explains how the system
works. Most of it describes the model your AI AGENTS operate in.

WHO USES WHAT
─────────────
Most fest commands exist for AI AGENTS. They plan and run festivals with
`fest next`, `fest create`, `fest validate`, and the workflow commands. As a
HUMAN operator you rarely touch those directly.

If you're a human, set this up once and you're done:

  # 1. Shell helpers (adds `fgo` and `fls`). Add to ~/.zshrc (or ~/.bashrc):
  eval "$(fest shell-init zsh)"          # use `bash` for bash

  # 2. Tab completion. Add to ~/.zshrc (or ~/.bashrc):
  source <(fest completion zsh)          # use `bash` for bash

Then your day-to-day is four commands:

  fls              Quick festival list           (wraps `fest list`)
  fgo <name>       Jump into a festival directory (wraps `fest go`)
  fest watch       Live view of a festival's in-progress state
  fest show        Festival details (status, progress, node ref)

The rest of this guide is the model your agents work in: useful background,
not something you need to memorize to drive the system.

WHAT IS FESTIVAL METHODOLOGY?
─────────────────────────────
Festival Methodology is a goal-oriented project management system designed
for AI agent workflows. It organizes work into a 3-level hierarchy:

  Festival → Phase → Sequence → Task

  • Festival: The complete project (e.g., "Add Authentication System")
  • Phase:    Major milestone (e.g., "001_PLAN", "002_IMPLEMENT")
  • Sequence: Related group of tasks (e.g., "01_database_schema")
  • Task:     Individual work item (e.g., "01_create_users_table.md")

fest operates on a `festivals/` workspace. That workspace commonly lives inside
a CAMPAIGN: a git-native workspace AND memory layer (managed by the `camp` CLI)
that also holds your projects, intents, and cross-festival context.
  <campaign>/
  ├── .campaign/    # Campaign memory: intents, work items, config (via camp)
  ├── projects/     # Your project repositories
  └── festivals/    # Festival workspace (what fest manages)
      ├── .festival/    # Methodology resources and templates
      ├── planning/     # Festivals being planned
      ├── ready/        # Ready for execution
      ├── active/       # Currently executing festivals
      ├── ritual/       # Recurring festivals
      ├── chains/       # Linked/chained festival workflows
      └── dungeon/      # Final/non-active states (completed/, archived/, someday/)

fest also works standalone: `fest init` creates a bare `festivals/` workspace
with no campaign required. A campaign just adds the surrounding workspace and
durable memory when you want it.

FESTIVAL TYPES
──────────────

  standard (default)    Full planning + implementation
  implementation        Execution-only (requirements already exist)
  research              Investigation and exploration
  ritual                Recurring/repeatable processes

  Create: fest create festival --name "<name>" --type <type>

PHASE TYPES
───────────

Every phase has a type that determines its structure:

  planning         WORKFLOW.md, inputs/, decisions/, plan/ (no sequences)
  implementation   Numbered sequences + numbered task files + quality gates
  research         WORKFLOW.md, sources/, findings/, analysis templates
  ingest           WORKFLOW.md, input_specs/, output_specs/
  review           Freeform (PHASE_GOAL.md with review criteria)
  non_coding_action  Freeform (PHASE_GOAL.md with action items)

  Create: fest create phase --name "IMPLEMENT" --type implementation

ESSENTIAL COMMANDS (LEARN THESE FIRST)
──────────────────────────────────────

  fest understand           Show methodology overview
  fest understand structure Learn the 3-level hierarchy in detail
  fest understand tasks     CRITICAL: When to create task files

  fest status               View current festival progress
  fest next                 Get the next task to work on
  fest validate             Check festival structure for issues

CREATING FESTIVALS
──────────────────

  fest create festival      Create a new festival (--type to set type)
  fest create phase         Add a phase (--type to set phase type)
  fest create sequence      Add a sequence to a phase
  fest create task          Create individual task files
  fest gates apply          Add quality gates to implementation sequences

NAVIGATION
──────────

  fest go                   Navigate to festivals directory
  fest go active            Jump to active festivals
  fest go <festival>        Jump to a specific festival
  fest go <phase>           Jump to a phase directory
  fest list                 List all festivals with status

THE FEST NEXT LOOP (how agents execute)
───────────────────────────────────────

A festival plan is a self-driving work loop, and `fest next` is the engine. It
reads the festival structure, works out what to do next (respecting task
dependencies and priority), and returns that step WITH the full task content and
layered goals inline, so an agent has everything it needs to execute. It walks
the whole plan for you: tasks, workflow steps, and the quality gates between
phases.

The loop:

  fest next                 What to do now (full context inline)
  # ...do the work...
  fest task completed       Mark it done, then loop again
  fest next                 Next step
  # repeat until the festival is complete

  fest next --json          Same, machine-readable for automation
  fest next --path          Just the next task's file path (for piping)
  fest next --short         Task path plus a status line

Because `fest next` always hands the agent the current step in full, agents
rarely need to load the whole methodology up front. Run the loop, read details
just in time. This is why a well-formed festival behaves like a highly capable,
long-running work loop rather than a static plan.

QUICK START
───────────

  1. Enter a festival:        fest go active/<name>     (humans: fgo <name>)
  2. Sanity-check structure:  fest validate
  3. Run the loop:            fest next, do the work, fest task completed, repeat

TRY IT: STANDALONE WORKFLOW (the simplest loop)
───────────────────────────────────────────────

The quickest way to feel the loop, no festival needed. In ANY directory:

  fest create workflow demo    WORKFLOW.md + a tracked run
  fest next                    First step, in full
  fest workflow advance        Done, move to the next step
  fest workflow runs           Run history

Best for simpler, linear loops. For complex work, create a full festival: the
default (standard) type scaffolds INGEST and PLANNING phases that walk an agent
through breaking requirements down into a structured plan before implementation.
Full detail: fest understand loop

CUSTOMIZING TEMPLATES
─────────────────────

The scaffolds fest generates are yours to shape. Methodology templates live in
`.festival/templates/` (festival, phase, sequence, task). Edit them to change
what `fest create` produces, or add a custom type there (see `fest types`).
Refresh the built-in set with `fest system update`. For repeatable per-festival
snippets, `fest templates create/apply` manages `{{variable}}` templates.

KEY PRINCIPLES
──────────────

  • STEPS NOT TIME: Think in terms of steps to reach a goal, not time estimates
  • READ BEFORE WRITING: Always understand existing structure first
  • GOAL FILES FIRST: Every level needs its goal document
  • IMPLEMENTATION = SEQUENCES + TASKS: Implementation phases MUST have
    sequence directories and numbered task files
  • WORKFLOW PHASES: Planning, ingest, and research phases use WORKFLOW.md
  • VALIDATE OFTEN: Run fest validate before and after changes
  • PARALLEL NUMBERING: Nodes with the same number can run in parallel
    (applies to phases, sequences, and tasks)
  • SEQUENTIAL BY DEFAULT: Complete tasks in order within sequences

THE FESTIVAL STACK
──────────────────
fest ships as part of the Festival stack (camp + fest + festival). Install or
update the whole stack with one of:
  npm install -g @obedience-corp/festival
  brew install --cask Obedience-Corp/tap/festival
  yay -S festival-bin
Refresh methodology templates in an existing workspace with: fest system update

For detailed methodology documentation:
  fest understand methodology

For all available commands:
  fest --help
